# 多跳搜索机会实验分析

## 1. 为什么先做这个门禁

前一轮成本奖励实验中，C 将搜索几乎降到零，同时 EM 明显下降。继续调小 `lambda` 只有在原策略确实存在“答对但多搜、且部分搜索可省”的情况下才有意义。本轮因此不训练新模型，而是先固定 B/control20，在显式多跳数据上回答三个问题：模型是否会多次搜索、正确答案是否依赖多次搜索、是否存在可识别的冗余搜索。

这是一次可行性审计，不是新的 B/C 效果对比。`NO-GO` 表示当前观测条件不足以支持后续成本实验，并不表示成本感知方向在其他策略或数据上永远无效。

## 2. 数据与指标

评测从 HotpotQA 和 2WikiMultiHopQA 的 dev split 各固定抽取 128 题，共 256 题。推理使用 B/control20、BM25 top-3、最多 4 次真实搜索、单次随机采样和 256 的最大 response 长度。逐题以规范化 exact match（EM）判断正确性，以实际执行的检索调用计数 `S`。

`hop_proxy` 只是标注 supporting title 的去重数量，不是语义上的 oracle hop 数，也不能推导“某题理论上必须搜索几次”。因此，本分析只陈述模型实际做了什么，不把数据集的多跳标签等同于所需调用次数。

## 4. 为什么第二次搜索不算优化空间

仅看 `S=2` 的数量可能误以为模型偶尔在做两步检索，但逐轨迹检查否定了这一解释：

- 8 题全部答错、全部 response clipped、全部包含非法动作；
- 7/8 的第二个 query 与第一个 query 完全相同；
- 7/8 没有可提取的最终答案；
- 其余 226 条未截断轨迹全部恰好搜索一次。

因此，第二次调用与“先找中间实体，再围绕实体继续搜索”的可解释链路不符。更稳妥的判断是：模型在长度上限附近重复生成了搜索格式，评测器仍执行了动作，随后输出没有正常闭合。这些调用不应被包装成多跳推理能力，也不能作为冗余搜索优化的正样本。

没有任何 `S>=3` 轨迹，预注册的第三次搜索冗余启发式自然没有适用样本。`redundant_search_candidates.csv` 为空不是“证明没有冗余”，而是根本没有达到可检测区间。

## 5. NO-GO 的含义

8 项门禁中只有“总正确数至少 20”通过。以下关键条件均失败：正确且 `S>=2` 为 0（要求至少 8）、正确题中 `S>=2` 比例为 0（要求至少 20%）、`S>=3` 为 0（要求至少 10）、冗余候选为 0（要求至少 5）。同时，截断率和非法动作题比例均为 11.72%，超过 5% 的质量上限。

当前 B 策略已经把几乎所有题压成一次搜索。如果直接继续训练成本奖励，优化器能学到的最容易行为仍是“从一次降到零次”，而不是“从三次降到两次并保持答案正确”。这与上一轮 no-search collapse 的风险方向一致。所以停止新成本分支是节省预算且符合预注册规则的决策，不是实验失败后临时改口径。

## 6. 结论边界与后续条件

本轮只有一个 checkpoint、一个 seed、每题一次采样和 256 道固定子集；EM 也不能覆盖语义等价答案。最大 response 256 造成 11.72% 截断，说明它适合低成本门禁，但不足以完整刻画长链规划能力。本轮没有比较更长 response、不同 prompt、不同检索器或专门训练过多跳搜索的 checkpoint。

只有当后续方案先让基线产生稳定、有效、可解释的迭代搜索，才值得重新开启成本分支。最低证据应包括：多次搜索出现在未截断轨迹中；至少一批正确题使用两次以上搜索；query 随中间证据发生变化；然后再预注册“减少调用但不显著损失 EM”的成本对照。不要为了得到 GO 而事后放宽本轮阈值。

## 7. 面试时可以怎么讲

> 我先复现了 Search-R1-small，并观察到直接加入搜索成本会导致 no-search collapse。为了避免继续盲调奖励，我设计了一个多跳搜索机会门禁：固定 control checkpoint，在 HotpotQA 和 2WikiMultiHopQA 的 256 题上保存逐题轨迹。结果 96.9% 的题只搜索一次，所有答对题也只搜索一次；仅有的 8 条二次搜索都伴随截断和非法动作，多数还重复 query。于是我按预注册标准做出 NO-GO，没有继续烧 GPU。这个负结果说明，成本优化前应先确保策略具备真实的迭代检索行为，否则奖励只会鼓励少调用，而不会学到更高效的规划。

不要表述为“证明多跳数据只需要一次搜索”或“证明成本奖励无效”；本轮只证明当前 checkpoint、采样配置和固定子集没有提供足够的可观察优化空间。
